> מטרה: לפני כתיבת קוד — לראות במדויק **מה קיים, מה חסר, ומה אופי העבודה** לכל אזור, כך שכל פיצ'ר ב-[10-roadmap](10-roadmap.md) ייצא לדרך עם תמונת פתיחה אמיתית. מסתמך על ה-AS-IS המתועד ([../specs/](../SPEC.md)) ועל הטבלאות ב-[11-appendix](11-appendix.md).

## 1. תמונת על

| אופי העבודה | אזורים | משמעות |
|---|---|---|
| **נשאר כמעט כמו שהוא** (תיקונים נקודתיים) | ספריית אימונים + פרסר + פופאפים, פתקים, מבנה הלקוח, shared/types | הנכסים הכי חזקים של הקוד |
| **נשמר ומורחב** (הרחבה משמעותית) | מודול התוכניות (Programs), קבוצות + פרטי קבוצה, נוכחות + דאשבורד, מנוע האזורים | הבסיס קיים — ה-TO-BE מוסיף עליו |
| **שכתוב ארכיטקטוני** (הלוגיקה נשארת, הדגם מתחלף) | שכבת האירועים (מסונתז → ישויות יציבות), שכבת הנתונים (JSON → Postgres), Apply Program | עבודת F0.1/F1.2 — המקום שבו אסור לחסוך |
| **חדש לגמרי** | Auth+הרשאות, i18n/RTL, עונות, מתקנים/מסלולים, סניפים, שיבוץ, קליטה, אנשי מקצוע, תקשורת, תשלומים, חנות/מגזין, מנוע דגלים, PMC | כמו שמתוכנן ב-roadmap |

**הערכה גסה לשלב 1**: ~40–50% מה-UI הדרוש כבר קיים כקומפוננטות ניתנות להתאמה; רוב העבודה הכבדה היא תשתית (F0) ודגם-נתונים (F1.2), לא מסכים.

## 3. מסקנות לקראת הבנייה

1. **ההשקעה ב-dev לא הייתה לחינם**: הוויזארד+לוח התוכנית, הפרסר, פרטי הקבוצה והנוכחות, ומצבת ה-UI של הלוח — נכסים אמיתיים שיישארו. הכבד באמת קיים: שכבת אירועים יציבה (F1.2) ותשתית F0.
2. **סדר העבודה ההגיוני מתאשר**: F0.5 (לבנות ירוק) → F0.1 (DB) → F0.2/F0.3 (auth+middleware) → F1.2 (מופעים) — כי מ-2.2 והלאה הכל נשען עליהם.
3. **היכן אין לזגזג**: F1.2 הוא השלב שבו "מסתמן על עובד" מפסיק להיות מספיק — בלי מופעים יציבים אין נוכחות, שיבוץ, אימונים משויכים או פציעות. ה-UI הקיים מקסים את הסיכון.
4. כל באג AS-IS ממופה לפיצ'ר שסוגר אותו — אין "ניקוי כללי", יש סגירה בתוך העבודה המתוכננת.
