# TO-BE 01 — משתמשים, תפקידים והרשאות

> איפיון רצוי · מסמך ראשי: [SPEC.md](SPEC.md) · החלטות: D1, D2, D8, D12

## 1. קיים ב-dev

אין כלל מערכת משתמשים — אין Auth, אין הרשאות, השרת פתוח לחלוטין (CORS פתוח, אין login). כל מסמך ההרשאות הוא יצירה מחדש.

## 2. התפקידים (USR-1)

| תפקיד | תיאור |
|---|---|
| **מאמן/ת ראשי/ת (Owner)** | בעל/ת המועדון. רואה הכול: כל הקבוצות, הספורטאים, הנתונים הרפואיים, התשלומים, הצ'אטים של כל המאמנים, הגדרות המערכת. רק הוא מוסיף מאמנים, מגדיר את הקטלוגים (ענפים, מבחנים, שיטות אזורים) ורואה סיכומים פיננסיים מלאים. |
| **מאמן/ת (Coach)** | מאמן עוזר/שכיר. רואה ומנהל רק את הקבוצות והספורטאים שהוקצו לו; כולל נוכחות, תוכניות וצ'אטים שלהם. לא רואה כספים (אלא אם הOwner החליט אחרת) ולא רואה קבוצות של מאמנים אחרים. |
| **מנהל/ת סניף (Branch Manager)** (D18) | אחראי/ת על סניף אחד או יותר: מנהל/ת את הקבוצות, הצוות והמתאמנים של הסניף, מוסיף/ה מדריכים ומאמנים לסניף, רואה נתונים מצטברים של הסניף. לא רואה סניפים אחרים ולא את הגדרות המועדון כולו. |
| **מדריך/ה (Instructor)** (D18) | תפקיד הדרכה (למשל בוגרים שמדריכים קבוצות ילדים): מנהל מפגשים ונוכחות של הקבוצות שהוקצו לו ומסמן ביצוע. **לא** עורך תוכניות, לא ניגש לכספים/נתונים רפואיים מלאים (אלא אם הורחב מפורשות). |
| **איש/ת מקצוע (Professional)** (D22) | תזונאי/ת, פיזיותרפיסט/ית — וכל מומחה שהטננט יגדיר (קטלוג פתוח, D9). עובד בשני מצבים: **פנימי** (איש צוות המוקצה לקבוצות/ספורטאים) או **חיצוני** (מנהל לקוחות משלו דרך קישורים מאושרים). פירוט מלא — סעיף 9. |
| **ספורטאי/ית (Athlete)** | רואה רק את עצמו/ה: התוכנית האישית, אימונים שהוקצו, הנוכחות שלו, הטסטים והאזורים שלו, היעדים שלו, התשלומים שלו, צ'אט עם המאמנים שלו, והמגזין. |
| **הורה/אפוטרופוס (Guardian)** | רואה ומנהל את הילדים שלו בלבד: תוכנית הילד, דיווח ביצוע בשמו, נוכחות, הודעות, תשלומים, דוחות התקדמות. מספר ילדים תחת חשבון אחד. |

**הרשאות נוספות נדרשות**:
- **USR-2** — כל ישות נשלטת בהרשאות בצד השרת (לא רק ברינדור): מאמן שלא שייך לקבוצה מקבל 403 גם בקריאת API ישירה.
- **USR-3** — **פרטיות בין ספורטאים**: ספורטאי/הורה לא רואה לעולם נתונים של ספורטאי אחר — לא פציעות, לא תשלומים, לא נוכחות, לא צ'אטים. מדדים מצטברים של קבוצה (למשל פילוח רמות) — **[פתוח]**: האם להציג לספורטאים מספרים אנונימיים (percentile) או לא.
- **USR-4** — ה-Owner יכול להסתיר שדות ספציפיים גם ממאמנים (למשל: סכומי תשלום של ספורטאי, פרטים רפואיים מסוימים) — הגדרת הרשאות ברמת שדה **[פתוח: כמה גרנולריות בגרסה הראשונה]**.

### 2.1 משתמש אחד, כמה תפקידים (USR-12) (D24)

בפועל אנשים לובשים כמה כובעים — המערכת מתוכננת לזה מהיסוד:

- **חשבון אחד, N תפקידים**: לכל משתמש רשימת תפקידים (`roles: []`), ולכל תפקיד — הקצאות משלו (סניף/קבוצה/ספורטאי). למשל: שירה = מנהלת סניף ת"א **+** מאמנת של "ראשנים" **+** מדריכה של "דגיגונים".
- **הרשאה = איחוד (union) של המענקים**, בתוך תחום ההקצאה של כל תפקיד: מנהלת הסניף רואה את כל הסניף; כמאמנת — עורכת תוכניות ל"ראשנים"; כמדריכה — מסמנת נוכחות ל"דגיגונים" (ולא עורכת להם תוכניות).
- **כלל התנגשות**: אותו משתמש עם שני תפקידים על אותו משאב (מאמן + מדריך על אותה קבוצה) — התפקיד **החזק יותר** תקף; אין "הפחתת" הרשאות. אין מצב שתפקיד אחד חוסם את השני.
- **מצבים מובנים**: Owner שגם מאמן (הכל + פרופיל ספורטאי פרטי — USR-6); מאמן שגם מדריך; מנהל סניף שגם מדריך; **איש מקצוע שגם מאמן** (תזונאי שגם מאמן קבוצה — מקבל גישת מאמן + גישת תזונאי בנפרד).
- ה-UI מציג את הכובעים הפעילים ומאפשר החלפת הקשר (למשל, "מסך מנהל סניף" לעומת "מסך מאמן"), אבל מבחינת השרת אין מצב "משתמש מסוג אחד" — רק איחוד מענקים מאומת בכל בקשה.

## 3. אפוטרופסות ומעבר שליטה (USR-5)

- מתאמן נוצר תמיד עם "מנהל" — הורה/אפוטרופוס אחד או יותר, או עצמו (מבוגר).
- **ילד קטן (3 ומעלה)**: החשבון מנוהל ע"י ההורה — כל הדיווח, ההודעות והתשלומים עוברים דרך חשבון ההורה. אין לילד כניסה משלו עד שה-Owner/הורה מאשר.
- **מעבר לשליטה עצמית**: לפי **יכולת והחלטה** (D8 — לא אוטומטי לפי גיל): הוספת כניסה לספורטאי מנוהל בשלב שההורה/המאמן קובעים; בתקו�ת המעבר שניהם רואים.
- קשרי משפחה: מספר הורים לילד; הורה אחד לכמה ילדים; הנחת אחים בתשלומים (יימשך ב-[07-payments.md](07-payments.md)).
- כניסה ראשונה: הזמנה באימייל/טלפון מהמאמן; הגדרת סיסמה עצמית.

## 4. המאמן כספורטאי (USR-6)

- לכל משתמש מאמן (Owner/Coach) אפשרות לפרופיל ספורטאי **פרטי לחלוטין** — רק הוא רואה: תוכנית אישית, לוח אישי, טסטים ואזורים.
- היומן של המאמן = שכבות שניתנות לסינון: האימונים האישיים שלי / מפגשי הקבוצות / התחייבויות אישיות (שיחות, משימות) — הכל בלוח אחד עם מתגי תצוגה.

## 5. ריבוי מועדונים וסניפים (Multi-tenancy) (USR-7, USR-10)

- המערכת מוכרת למאמנים עצמאיים **ולמועדונים**: כל מועדון = tenant מבודד (הנתונים, הקטלוגים וההגדרות שלו).
- **היררכיית ארגון** (D18): `מועדון (tenant) → סניפים → קבוצות → מתאמנים`. מאמן עצמאי יכול להסתדר בלי סניף כלל (סניף אחד מרומז); מועדון גדול — כמה סניפים, ולכל סניף מנהל, צוות (20–30 אנשי צוות לכל המועדון בגודל טיפוסי), קבוצות וספורטאים (200–300 למועדון בגודל טיפוסי).
- **הרשאות לפי היררכיה**: Owner רואה הכל; מנהל סניף — את הסניפים שלו; מאמן/מדריך — את הקבוצות שהוקצו לו (גם אם מפוזרות בין סניפים).
- העברת ספורטאי/קבוצה בין סניפים — בסמכות ה-Owner ומנהלי הסניף, עם שימור היסטוריה.
- בעל/ת מאמן יכול/ה להיות Owner של יותר ממועדון אחד (מבחן עתידי למודל העסקי).
- כל שאילתה מוגבלת ל-tenant ברמת השרת (row-level scoping) — אין דרך להגיע לנתוני מועדון אחר גם בנתיב API ישיר.

## 6. אימות וכניסה (USR-8)

- כניסה באימייל או טלפון + סיסמה (D14: ענן; D15: תשתית חינמית — המימוש ב-[09-architecture.md](09-architecture.md)).
- איפוס סיסמה במייל; פרופיל משתמש בסיסי — שם, טלפון, תמונה.
- הרשאות נאכפות בכל endpoint; token קצר-טווח.
- **[פתוח]** כניסה עם OTP ב-SMS? (תלוי ספק חינמי; ברירת מחדל: אימייל בלבד).

## 7. ניהול משתמשים (USR-9)

- **ארכוב ולא מחיקה**: ספורטאי שעוזב מועבר לארכיון — ההיסטוריה (נוכחות, תשלומים, טסטים, צ'אטים) נשמרת ונגישה ל-Owner; מוסתר מהרשימות הפעילות.
- פעולות מנהל: הזמנת משתמשים, השעיה, שינוי תפקיד, העברת ספורטאי בין מאמנים/קבוצות.
- יומן פעולות בסיסי: מי שינה מה (רלוונטי במיוחד לנתונים רפואיים ותשלומים).
- **אופציה עתידית (לא בפיילוט)**: **מנהל/ת משרד (Operations)** — רישומים, תשלומים, לוגיסטיקה ותיאומי תחרויות, **ללא** גישה לנתוני אימון/רפואה/צ'אטים. המודל תומך בזה חינם: זהו רק תפקיד נוסף בקטלוג (USR-12 — הרכבת תפקידים) כשמועדון ידרוש את זה.

## 9. אנשי מקצוע — תזונאים ופיזיותרפיסטים (USR-11) (D22)

**מי**: תזונאי/ת, פיזיותרפיסט/ית — וקטלוג מומחים פתוח להגדרה פר-טננט (פסיכולוג ספורט, רופא, מאמן כוח וכו') — עקרון D9.

### 9.1 שני מצבי עבודה

| מצב | משמעות | גישה |
|---|---|---|
| **פנימי (Internal)** | איש/ת צוות בטננט — מוקצה לקבוצות/ספורטאים כמו מאמן | לכל הספורטאים בהקצאה, לפי הרשאות התחום (9.2) |
| **חיצוני (External)** | עובד/ת עצמאי/ת עם לקוחות משלו/ה (אולי מכמה מועדונות) | **ClientLink** — קישור שנוצר בהסכמת ההורה/ספורטאי (או באישור ה-Owner) המעניק גישה מצומצמת לספורטאי מסוים, עם תוקף אפשרי |

- איש מקצוע חיצוני מקבל **סביבת עבודה משלו** ("הלקוחות שלי"): רשימת לקוחות, התוכניות שכתב, לוז פגישות ותיאום מול המאמן — בלי לראות דבר מעבר למקושר אליו.
- **פרקטיקה עצמאית — Practice Tenant (D23)**: איש/ת מקצוע יכול/ה להחזיק **טננט משלו** — עסק עצמאי שמנהל לקוחות, תוכניות, לוז פגישות ומבחנים משלו, **בלי קשר למועדון כלשהו**: לקוחות פרטיים נוצרים ישירות בטננט שלו (מנהל/ת אותם לבד), וספורטאים מועדוניים מקושרים דרך ClientLink. המערכת משרתת בכך את כל שוק אנשי המקצוע בספורט, לא רק דרך מועדון. **מימוש: עתידי** — אחרי ייצוב המוצר המועדוני; הדגם תומך מיום 1 (`tenantType: club|practice` נכנס לסכמה כבר ב-F0.1).
- **[פתוח]**: האם איש מקצוע חיצוני גובה תשלום דרך המערכת (PAY)? המלצה: לדחות בשלב הזה.

### 9.2 הרשאות לפי תחום (Specialty Scoping)

| נתון / פעולה | תזונאי/ת | פיזיותרפיסט/ית |
|---|---|---|
| אימונים מתוכננים + ביצוע בפועל + עומס (MON) | קריאה | קריאה |
| טסטים, אזורים, יעדים ומרוצים | קריאה | קריאה |
| משקל/גובה/נתוני גדילה | קריאה + כתיבה | — |
| פציעות והיסטוריית פציעות | — (חסום כברירת מחדל) | קריאה + כתיבה — **בעלות על רשומת הפציעה והשיקום** |
| נוכחות / כספים | — | — |
| כתיבה: **תוכנית תזונה** (NutritionPlan, מקושרת ליעד/מרוץ) | ✓ | — |
| כתיבה: **תוכנית שיקום** (RehabPlan — שלבים, מגבלות, תרגילים, קריטריוני חזרה) | — | ✓ |
| **הוספת מפגשים ללוז** (טיפול/שיקום/פגישת ייעוץ) | פגישת ייעוץ בלבד | ✓ מפגשי שיקום |
| פגישות ותורים + תזכורות (COM-4) | ✓ | ✓ |
| צ'אט עם ספורטאי/הורה | ✓ | ✓ |

- הטננט יכול להרחיב/לצמצם את המטריצה בהגדרות, לפי specialty.
- **כל גישה לנתוני ספורטאי מתועדת ביומן הפעולות** (USR-9) — במיוחד נתונים רפואיים.

### 9.3 זרימות עבודה

- **תזונאי/ת**: רואה עומס, מגמות ומרוצים → כותבת NutritionPlan מקושרת ליעד → תזונת המרוץ ממלאת את `Goal.plan.nutrition*` הקיים → מוצגת בפורטל הספורטאי/הורה.
- **פיזיותרפיסט/ית**: רואה אימונים, עומס ופציעות → כותב/ת RehabPlan (שלבים, מגבלות, תרגילים, קריטריוני חזרה) → המגבלות **זורמות אוטומטית לבונה התוכניות** (PLAN-5) ולדגלים (MON-4) → מזמן/ת מפגשי שיקום בלוז → סוגר/ת את הפציעה עם אישור חזרה לאימון מלא.
