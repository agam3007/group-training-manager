# TO-BE 09 — ארכיטקטורה, תשתית וטכנולוגיה

> איפיון רצוי · מסמך ראשי: [SPEC.md](SPEC.md) · החלטות: D7, D14, D15, D17
> מסמך זה מגדיר את התשתית שתעמוד מאחורי כל המודולים. ממשיך את [../specs/01-architecture.md](../specs/01-architecture.md) (AS-IS).

## 1. קיים ב-dev

React 19 + Vite + TS מול Express 5 + TS; טיפוסים משותפים (`shared/types`) — יתרון ארכיטקטוני אמיתי שנשמר; מסד נתונים = קובץ JSON אחד (קריאה/כתיבה מלאה לכל בקשה, תנאי מרוץ מובטחים בריבוי משתמשים); אין auth, אין ולידציה; פורט מוקשח; dnd-kit מותקן ולא בשימוש; `tsc -b` נכשל (באג 4.32).

## 2. עקרונות (ARC-0)

1. **ענן, ריבוי-מועדונים, ריבוי-משתמשים** (D14) — הקובץ המקומי מתאים רק למשתמש אחד; מהרגע שיש הורים וספורטאים נכנסים — DB אמיתי.
2. **חינמי כרגע** (D15) — המחסום הוא בחירת שירותים בתחום החינמי עם נתיב שדרוג חלק, לא פשרות בעיצוב.
3. **סנסביליות** (D7) — לא לבנות ל-100 מועדונים ביום הראשון, אבל כן לבנות מבנה שמכבד tenant מהשורה הראשונה (row-scoping, מזהים יציבים) כי שינוי זה אחר-כך הוא היקר ביותר.

## 3. המלצת תשתית (ARC-1) — **[פתוח לאישור, הצעה מובילה]**

**אופציה מומלצת — Supabase (חינם):**
| צורך | שירות | מגבלת חינם |
|---|---|---|
| DB | Supabase Postgres | 500MB, מספיק לשנים של טננטים בודדים |
| Auth | Supabase Auth (אימייל+טלפון, JWT) | 50,000 MAU |
| אחסון קבצים | Supabase Storage (וידאו/תמונות/קבלות) | 1GB |
| Realtime | Supabase Realtime (צ'אט, לוח חי) | כלול |
| Edge functions / cron | Supabase Functions | מוגבל אך מספיק ל-digestים |
| אפליקציית לקוח | Vercel/Netlify חינם | נדבך סטטי |
| ניטור שגיאות | Sentry free tier | 5K אירועים/חודש |

**אופציה חלופית** (אם רוצים DB-מנוהל נפרד): Neon (Postgres חינם) + Auth.js + Cloudflare R2 (10GB חינם) + Fly.io — גמיש יותר, אבל מרכיבים יותר.
בשתי האופציות ה-API שלנו (Express) נשאר — הוא מול ה-DB ומול Auth של הספק; הלקוח נשאר React+Vite. השרת בענן (Render/Fly חינם) לצד Supabase, או ב-Edge שלהם.

### 3.1 השוואה מעמיקה — לקבלת ההחלטה

**מה שהמערכת באמת צריכה**: Postgres מרובה-טננט (מיד), Auth מלא עם הזמנות/תפקידים (מיד — F0.2), אחסון קבצים (חשוב; וידאו בקישור חיצוני כברירת מחדל — ARC-8), Realtime לצ'אט (שלב 2), Cron להתראות (שלב 2+).

| ממד | **Supabase** | **Neon + R2 + Auth.js** |
|---|---|---|
| DB | 500MB, 2 פרויקטים; **השהיה אוטומטית אחרי שבוע ללא פעילות** (מנוטרלת ב-ping מתוזמן; נעלמת ב-Pro) | 512MB; autosuspend עם התעוררות מהירה; branching לפיתוח |
| Auth | **מובנה**: אימייל/OTP/טלפון, JWT, RLS; הזמנות נבנות ב-API שלנו על גביו | בנייה עצמית (Auth.js): סשנים, איפוס סיסמאות, אימיילים — **שבועות עבודה ב-F0.2** |
| אחסון | 1GB | **R2: 10GB + אפס עלות egress** — יתרון אמיתי לקבצים כבדים |
| Realtime | **מובנה** — הצ'אט של שלב 2 נשען עליו ישר | אין — SSE/WebSocket בנייה עצמית או פולינג |
| Cron/Edge | Edge functions + pg_cron | ספק חיצוני (GitHub Actions/Render cron) |
| גיבויים | גיליון-1-יום בחינם + pg_dump עצמאי | אחריות מלאה שלנו |
| מרכיבים לתחזק | **פלטפורמה אחת** | 4 מקורות (Neon + R2 + Auth + host) |
| תקורת הקמת שלב 0 | **נמוכה** | גבוהה |
| מסלול שדרוג | Pro $25/חודש — העלות הראשונה האמיתית, סבירה כשהפיילוט חי | pay-as-you-go זול בנפחים קטנים |
| נעילת ספק | בינונית — Postgres סטנדרטי, יציאה אפשרית | נמוכה |

**ההמלצה נותרת Supabase**, מהנימוקים:
1. **Auth הוא שלב-0 שלם** (F0.2: תפקידים, אפוטרופסות, הזמנות) — ספק שחוסך אותו מקזז את כל יתרונות החלופה.
2. **Realtime לצ'אט** — שבועות שנחסכות בדיוק בשלב 2, שבו נרצה להתקדם מהר.
3. מגבלת ה-1GB לא מפחידה: וידאו ארוך בקישור חיצוני מטריסטי (ARC-8); אם יידרש — **היבריד זול: R2 בצד לקבצים כבדים בלבד**.
4. ההשהיה האוטומטית: ping שבועי מ-GitHub Actions עד שהפיילוט רץ בפועל.
5. יציאה זמינה (Postgres סטנדרטי + יצוא ARC-10) — נעילה נסבלת.

**אם מגיעים למכסה** (סדר פתרונות, כולם בלי שכתוב): וידאו → R2; DB/פרויקטים → Pro ($25); אימייל יוצא → Resend.

## 4. מסד נתונים (ARC-2)

- **Postgres** מחליף את database.json. כל אוסף = טבלה; קשרי מפתח זר עם cascade מוגדר; `tenantId` בכל טבלה + אכיפה בשכבת השאילתות (ובהמשך RLS).
- **מיגרציה חד-פעמית** מ-database.json הקיים (15 אוספים): athletes, groups, athleteGroups, trainings, programs (+meso/planned/scheduled), trainingAssignments, attendances, notes, folders, events/overrides → המודל החדש (02), כולל תיקוני נתונים ידניים (מחרוזות-מספרים, שמות במערכי ספורטאים ישנים, סדרי קבוצה).
- Migrations ניהוליים (לא סכמה בקוד); גיבוי יומי (pg_dump מתוזמן) — גם בחינם.
- **ולידציה**: zod (או similar) על כל בקשה — 400 מובנה בשגיאות (מתקן את היעדר ה-400 ב-AS-IS); הטיפוסים ב-shared הופכים ל-single source לסכמות.

## 5. אבטחה (ARC-3)

- AuthN: JWT מספק ה-Auth; refresh; הפעלת חשבון בהזמנה (ללא הרשמה עצמאית — מאמן מזמין).
- **AuthZ בשרת על כל נתיב** (USR-2): middleware הבודק תפקיד + שיוך (Coach→קבוצות שלו, Guardian→ילדיו) + tenant.
- ולידציה, rate-limit בסיסי, טהור CORS לדומיין שלנו, הצפנת סיסמאות אצל הספק בלבד; נתונים רפואיים ותשלומים — גישה מתועדת (יומן פעולות USR-9).
- גיבויים + מחיקת משתמש ע"י עצמו **[פתוח: מדיניות שמירת נתונים/פרטיות לפי דרישות משפטיות]**.

## 6. לקוח (ARC-4)

- נשאר: React + Vite + TS + shared types; הרכיבים הקיימים עוברים כמו שהם לתוך המערכת החדשה (לוח, פופאפים, פרסר — כל ההשקעה ב-dev נשמרת).
- **ניהול שרת-מצב (Server state)**: React Query/TanStack Query — caching, invalidation, אופטימיסטיות; מחליף את ה-fetch-הידני הפזור (ומתקן את דפוס "כל עמוד טוען הכל").
- **PWA**: התקנה בבית, Web Push (COM-4), מצב שטח עמיד (SES-4). מובייל-ראשית לפורטל הספורטאי/הורה.
- **i18n + RTL/LTR** (D4): מהיום הראשון — מפתחות תרגום (HE ברירת מחדל, EN), `dir` דינמי, תאריכים/מספרים לוקאליים. כל טקסט חדש נכנס דרך מפתח. התוכן הקיים ב-DB נשאר כפי שנכתב (טקסט חופשי של המשתמשים).
- ניקויים מה-AS-IS: dnd-kit (לא בשימוש), Alert המת, ProgramCard הכפול, תיקון ייבואי CSS בשגיאת רישיות (4.34), תיקון alias ב-vite (4.33), החזרת `tsc -b` לירוק (4.32) — תנאי סף לכל עבודה חדשה.

## 7. מודול השרת (ARC-5)

- Express (או Fastify — **[פתוח]**, הצעה: להישאר ב-Express, מוכר וקיים) עם אותו מבנה routes; הוספת: middleware auth, ולידציה, בקרת tenant, שכבת services (attendanceService/dashboardService/notesService הקיימים — נשמרים ומורחבים).
- **עבודות רקע**: digest יומי (דגלים COM-4), גבייה חודשית (PAY-2), תזכורות מפגשים — cron פשוט; בחינם: cron חיצוני (GitHub Actions/Render cron) או pg_cron **[פתוח]**.
- Realtime: Supabase Realtime לצ'אט וללוח; נפילה לפולינג.

## 8. מוכנות AI ואינטגרציות (ARC-6) (D17, D2)

- **דגם נתונים נקי הוא התשתית ל-AI**: PerformanceLog מתועד מקור (coach/athlete/guardian/watch), מופעים יציבים, נוכחות היסטורית אמיתית, עומס מוגדר — על אלה יאומנו המודלים/ההמלצות. שלבי ה-AI:
  1. **עכשיו (ללא AI)**: מנוע הדגלים = כללים דטרמיניסטיים (MON-1).
  2. **שלב עתידי A**: המלצות אימון **המבוססות על בנק אימונים מוצלחים** (PLAN-8/DOM-13 — שליפת תבנית שהוכחה + התאמה לספורטאי/עומס/פציעות בעזרת LLM) + סיכום חודשי אוטומטי לדוח הורה.
  3. **שלב עתידי B**: ייבוא Garmin/Strava (D2) → ניתוח דפוסים, חריגות עומס, חיזוי עייפות.
- ממשק ייבוא מוגדר כבר עכשיו בסכמת PerformanceLog כך שהוספת ספק לא דורשת שינוי דגם.
- **[פתוח]**: איזה ספק LLM (כולל המלצות שמירת עלות) — בשלב הרלוונטי.

## 9. עלויות ושדרוג (ARC-7)

- **0 ₪**: כל השירותים לעיל בתוכניות החינמיות תומכים במועדון אחד עד כמה מאות משתמשים.
- נקודות שדרוג מתועדות מראש: אחסון וידאו (R2/1GB → תשלום לפי GB), MAU מעבר ל-50K, מסד מעבר ל-500MB — כולם pay-as-you-go ללא שכתוב.
- העסקה (מונטיזציה) — מחוץ לתחום האיפיון הטכני; המערכת נבנית multi-tenant כך שמודל Free/Paid למאמנים אפשרי בעתיד.

## 10. דרישות בלתי-פונקציונליות — NFR מספריים (ARC-8) (D18, D20)

| מדד | יעד |
|---|---|
| **גודל טננט מלא** | 300 ספורטאים + 30 צוות + ~400 הורים/משתמשי קצה ≈ **~800 חשבונות**; 3–10 סניפים; ~1,200 מופעים/שנה; ~40,000 רשומות נוכחות/שנה |
| **סקאלת מערכת (יעד שנה 1)** | עד **20 טננטים** (~16,000 חשבונות, ~3,000 פעילים בו-זמנית בשעות שיא 16:00–20:00) — בתוך תוכניות החינם; ללא שכתוב עד 100 טננטים |
| **זמני תגובה** | API: p95 < 400ms לקריאות רשימה, p95 < 150ms למפגשים ביומן; טעינת מסך שטח < 2 שניות במובייל 4G |
| **זמינות** | 99.5% (סביבות ~3.6 שעות/חודש); תחזוקות מתוזמנות בלילה |
| **Realtime** | צ'אט ולוח — השהיה מורגשת < 2 שניות |
| **אחסון** | תמונות/קבצים: ~5MB ממוצע; וידאו: העלאה עד 50MB בדחיסת שרת, **מכסת וידאו לטננט כמגבלת התשתית** (1GB בחינם ≈ עשרות סרטונים — וידאו ארוך דרך קישור YouTube ולא העלאה) |
| **דפדפנים** | Chrome/Safari/Edge שני גרסאות אחרונות; אנדרואיד 10+/iOS 15+; PWA מותקן נתמך |
| **עמידות נתונים** | גיבוי יומי, שחזור עד 30 יום אחורה; אין מחיקה פיזית (ארכיון — USR-9) |

- הסקאלה מכתיבה **pagination ואינדקסים** בכל רשימה (300 ספורטאים לא נטענים בעמוד אחד), ו-caching ללוחות תחת עומס שעות השיא.

## 11. מדיניות תאריכים ואזורי-זמן (ARC-9)

- **טננט = אזור זמן אחד** (ברירת מחדל `Asia/Jerusalem`; ניתן לשינוי בהגדרות הטננט).
- מופעים נשמרים כ-**תאריך+שעה לוקאליים** (לא UTC) — אין המרות בשכבות הביניים; השרת מבצע חישובי יום/שבוע לפי אזור הטננט.
- "היום" נקבע לפי אזור הטננט (לא לפי שעון השרת/הלקוח); לוחות מציגים לפי אזור הטננט.
- חוק ברזל: **אסור לערבב ייצוגי תאריך** (ISO-UTC מול לוקאלי מול "Week N, Day D" מה-AS-IS) — סוג אחד לתאריכי מופע; בדיקות יחידה לכל לוגיקת תאריכים (שעה קייצית, חצות, מעבר שנה).
- ה-legacy "Week N, Day D" נעלם עם ההגירה (F0.1) — שבועות מחושבים מתאריכים.

## 12. זכויות נתונים, יצוא ומחיקה (ARC-10)

- **יצוא עצמאי**: ה-Owner מייצא את נתוני המועדון (CSV/JSON); הורה/ספורטאי — את נתוניו בעזיבה.
- **מחיקה לפי בקשה**: מחיקת חשבון מוחקת זיהויים אישיים ושומרת רשומות כספיות/היסטוריות בצורה אנונימית (מטעמי חוק הגנת הפרטיות וחשבונאות) — מדיניות מפורטת **[פתוח: אישור משפטי בנספח]**.
- רגישות מיוחדת: נתונים רפואיים (פציעות, אלרגיות) ונתוני קטינים — גישה מתועדת (USR-9) וללא כניסה לכל צד שלישי (כולל רשתות פרסום — סעיף 13).

## 13. תשתית המונטיזציה (ARC-11) (D19)

- **פרסומות**: מוצגות רק בפורטל הספורטאי/הורה (מיקומים ב-[08](08-shop-and-content.md) CONT-4); **קונטקסטואלי בלבד — ללא פרופילינג משתמשים** (במיוחד קטינים); אין SDK מעקב בסביבת המאמן; כיבוי פר-טננט כהטבת מנוי עתידית.
- **מנויים עתידיים**: `plan` בטבלת הטננט (`free|pro`) + מגבלות מרכזיות מוגדרות מראש (מספר ספורטאים פעילים, אחסון וידאו, הסרת פרסומות) — המתג נבנה בשלב 0 כשדה, האכיפה בשלב המסחור. כך המעבר למנויים הוא קונפיגורציה, לא שכתוב.
- תשלום למערכת (עתידי) — דרך אותו מנגנון סליקה כמו לטננטים ([07](07-payments.md) שלב B), tenant הוא "משלם" בפני עצמו.

## 14. טלמטריה ומדידה (ARC-12)

- **אנליטיקס מוצר מובנה, לא צד-שלישי**: טבלת `events` פנימית, מתויגת טננט (למשל: `session_documented`, `plan_published`, `parent_active_weekly`, `feature_used`) — מזינה את ה-North Star, מדדי SPEC §6 ושערי [13](13-business-plan.md) §8. **ללא SDK מעקב חיצוני** כלל (עקבי עם ARC-11 — במיוחד קטינים); הפקה מצרפית בלבד לדוחות פנימיים.
- מה נמדד מיום 1: מפגשים מתועדים (North Star), פעילות שבועית לפי תפקיד, Time-to-First-Value לטננט חדש, שימוש בפיצ'רים (לניקוי dead features), שיעורי שגיאה.
- נתוני טלמטריה אישיים → לא משותפים לאף גורם חיצוני; שמירה מצטברת **[פתוח: תקופה]**.

## 15. קונבנציות API (ARC-13)

נקבעות סופית ב-F0.3, אבל הברירות מחדל כבר עכשיו כדי למנוע צ'ורצ'ורץ:
- REST תחת `/api/v1` (במקום הנתיבים הישנים); JSON בלבד; JWT ב-Bearer.
- **מעטפת שגיאה אחידה**: `{ error: { code, message, details? } }` + קודי 400/401/403/404/409 בהתאם ל-F0.3.
- **Pagination** בכל רשימה (cursor-based) — מחויב מה-NFR (300 ספורטאים בטננט); מיון וסינון בשרת.
- מזהים: UUID בלבד; שדות `createdAt/updatedAt` חוזרים בכל ישות.
- פעולות כספים ושינויי לוז רגישים → idempotency-key חובה.
